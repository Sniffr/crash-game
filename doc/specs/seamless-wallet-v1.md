# Seamless Wallet Integration Spec — v1

**Status:** Draft v1 · **Audience:** Casino operators integrating Galaxy Crash · **Date:** 2026-05-18

The casino operator owns the player, the wallet, KYC, and the license. Galaxy Crash owns the game round, the RNG audit trail, and the in-frame UX. Every bet and win round-trips through the operator's wallet API in real time. This document is the contract between the two sides.

---

## 1. Roles & data ownership

| Concern | Owned by |
|---|---|
| Player identity, KYC, AML, RG limits | Operator |
| Player wallet (deposits, withdrawals, balance, bonuses) | Operator |
| Game launch URL, iframe rendering | Galaxy Crash (the "Game") |
| Round outcome, RNG seeds, multipliers | Game |
| Bet ledger (immutable record of every debit/credit) | **Both** — each side keeps its own; reconciled daily |

The Game NEVER holds player money. Balance shown in the iframe is always sourced from the operator.

---

## 2. Glossary

- **Operator** — the casino integrating the Game.
- **Launch token** — short-lived opaque token the operator mints when the player clicks the game thumbnail; passed in the launch URL.
- **Session** — the lifetime of one player's iframe load. One session = many rounds.
- **Round** — one crash-game round. One round = one or many bets from this player (Aviator allows two concurrent bets).
- **Bet** — a single stake placed by the player on a round. Identified by `betId`.
- **txnId** — globally unique transaction id, generated by the Game, used for idempotency on the operator side.
- **Minor units** — integer cents/satoshi. EUR 1.50 → `150`. BTC 0.0001 → `10000` (8 decimals).

## 3. Game launch (Operator → Game)

The operator opens an iframe pointing at:

```
https://game.galaxy-crash.io/launch
  ?operator=acme
  &token=<opaque-launch-token>
  &currency=EUR
  &lang=en
  &lobby_url=https%3A%2F%2Fcasino.com%2Flobby
  &return_url=https%3A%2F%2Fcasino.com%2F
  &jurisdiction=MT
  &mode=real            (or "demo")
```

Required: `operator`, `token`, `currency`. All others optional.

The Game backend immediately calls `POST /authenticate` (§5.1) on the operator's wallet API to resolve the token. On success, the game UI loads. On failure, the iframe renders an error page with a "Return to lobby" button pointing at `return_url`.

## 4. Authentication & signing

### 4.1 Per-operator credentials

For each operator the Game stores:
- `operatorId` (slug, e.g. `acme`)
- `walletBaseUrl` (e.g. `https://wallet.acme-casino.com/v1`)
- `signingKey` (32-byte secret, shared)
- `apiKey` (sent in `X-API-Key` header — coarse routing/auth)

Operators receive these from the Galaxy Crash studio backoffice when onboarded.

### 4.2 Request signing (Game → Operator)

Every wallet call includes these headers:

```
X-API-Key:    <operator apiKey>
X-Timestamp:  1716000000          (unix seconds)
X-Nonce:      9f3e1c2a-...        (uuid v4, single-use; operators MUST cache for 10 min (see §4.2 rule 2))
X-Signature:  <hex-hmac-sha256>
Content-Type: application/json
```

Signing string:
```
METHOD + "\n" + PATH + "\n" + X-Timestamp + "\n" + X-Nonce + "\n" + SHA256(body-bytes)
```

HMAC-SHA256 over that string with `signingKey`, hex-encoded.

Operators MUST:
1. Reject if `|now - X-Timestamp| > 300s`
2. Reject on nonce reuse (cache nonces for 10 min)
3. Reconstruct the signing string and compare in constant time

### 4.3 Response signing (Operator → Game)

Operator responses MUST set `X-Signature` over:
```
HTTP_STATUS + "\n" + X-Timestamp + "\n" + SHA256(body-bytes)
```

The Game verifies the same way. Unsigned or mis-signed responses are treated as failures.

## 5. Wallet endpoints (Game calls Operator)

All endpoints are `POST`, JSON in / JSON out. Operator's base path is `walletBaseUrl`. Path suffixes:

### 5.1 `POST /authenticate` — resolve a launch token

Request:
```json
{
  "token": "opaque-launch-token",
  "ip":    "1.2.3.4",
  "userAgent": "Mozilla/...",
  "gameId": "galaxy-crash"
}
```

Response 200:
```json
{
  "playerId":     "op-acme-pid-9183",
  "displayName":  "lucky_falcon_42",
  "currency":     "EUR",
  "balance":      125075,
  "country":      "MT",
  "jurisdiction": "MT",
  "language":     "en",
  "rgLimits": {
    "maxBetMinor":   500000,
    "sessionEndsAt": 1716050000
  }
}
```

Errors: see §7.

### 5.2 `POST /balance` — refresh balance mid-session

Request:
```json
{ "playerId": "op-acme-pid-9183", "sessionId": "ses-..." }
```

Response 200:
```json
{ "balance": 125075, "currency": "EUR" }
```

### 5.3 `POST /bet` — debit (place a bet)

Request:
```json
{
  "playerId":   "op-acme-pid-9183",
  "sessionId":  "ses-...",
  "roundId":    "rnd-2026-05-18-00193847",
  "betId":      "bet-...-1",
  "txnId":      "txn-018f01d6-...-a1",
  "amountMinor": 10000,
  "currency":   "EUR",
  "gameId":     "galaxy-crash",
  "placedAt":   1716000010
}
```

Response 200:
```json
{
  "operatorTxnId": "op-tx-77182",
  "balanceMinor":  115075,
  "currency":      "EUR"
}
```

**Idempotency:** Same `txnId` replayed MUST return the same response and MUST NOT debit twice. Operators key idempotency on `(operatorId, txnId)`.

### 5.4 `POST /win` — credit (settle a winning cashout)

Request:
```json
{
  "playerId":  "op-acme-pid-9183",
  "sessionId": "ses-...",
  "roundId":   "rnd-2026-05-18-00193847",
  "betId":     "bet-...-1",
  "betTxnId":  "txn-018f01d6-...-a1",
  "txnId":     "txn-018f01d6-...-a2",
  "amountMinor": 24500,
  "multiplier":  2.45,
  "currency":  "EUR",
  "settledAt": 1716000023
}
```

Response 200:
```json
{
  "operatorTxnId": "op-tx-77191",
  "balanceMinor":  139575,
  "currency":      "EUR"
}
```

Wins for losing rounds are NOT sent — only credit on actual cashout.

### 5.5 `POST /rollback` — undo a bet

Request:
```json
{
  "playerId": "op-acme-pid-9183",
  "betTxnId": "txn-018f01d6-...-a1",
  "txnId":    "txn-018f01d6-...-a3",
  "reason":   "round_voided"
}
```

Response 200:
```json
{
  "operatorTxnId": "op-tx-77192",
  "balanceMinor":  125075,
  "currency":      "EUR",
  "status":        "rolled_back"
}
```

Rollback reasons: `round_voided`, `game_error`, `timeout`, `manual_void`.

Rollback is idempotent and MAY be called for a `txnId` the operator has no record of — in that case respond `200` with `"status": "noop"`.

### 5.6 `POST /round-end` — round summary (optional, fire-and-forget)

The Game POSTs this after every round closes. Operators MAY use it for analytics; the Game MUST NOT depend on a successful response.

```json
{
  "roundId":     "rnd-2026-05-18-00193847",
  "playerId":    "op-acme-pid-9183",
  "crashPoint":  3.42,
  "serverSeedHash": "...",
  "serverSeed":  "...",
  "bets": [
    { "betId": "bet-...-1", "txnId": "txn-...-a1", "amountMinor": 10000, "result": "win", "winTxnId": "txn-...-a2", "winAmountMinor": 24500, "multiplier": 2.45 }
  ]
}
```

## 6. Game-exposed endpoints (Operator → Game)

Operators authenticate to these with the same `X-API-Key` + signature scheme (§4.2), with the roles swapped (operator signs with their key; Game verifies).

### 6.0 Authentication errors

Operator→Game requests are authenticated by the same §4.2 HMAC scheme with roles swapped: the operator signs with its `signingKey` and the Game verifies. On any failure the Game responds with the §7 error envelope `{ "error": { "code": "...", "message": "..." } }` at the documented HTTP status; the request is not processed.

| HTTP | `code` | When |
|---|---|---|
| 401 | `INVALID_REQUEST` | Missing or malformed required signing header (`X-API-Key` / `X-Timestamp` / `X-Nonce` / `X-Signature`), or a header delivered as a non-string (e.g. duplicate header). |
| 401 | `INVALID_SIGNATURE` | Unknown `X-API-Key`, or HMAC signature does not match the reconstructed signing string (including body-bytes mismatch). |
| 401 | `STALE_REQUEST` | `X-Timestamp` is not a canonical unsigned-integer seconds string, or the skew \|now − ts\| exceeds the allowed window (default 300 s). |
| 401 | `NONCE_REUSED` | `X-Nonce` was already seen for this operator within the cache TTL (default 10 min); replay rejected. |
| 403 | `OPERATOR_PAUSED` | The operator account exists but is paused; calls are refused until resumed. |
| 500 | `INTERNAL` | Unexpected server error during verification. |

**Security note:** the nonce-replay check runs strictly *after* signature verification passes. A request with an invalid or forged signature never consumes a nonce, so an attacker cannot poison a legitimate operator's nonce cache.

See §4.2 for the canonical signing string construction and §7 for the error envelope shape.

### 6.1 `GET /v1/health`

```json
{ "ok": true, "version": "1.4.2", "gamesAvailable": ["galaxy-crash"] }
```

Unauthenticated. For monitoring.

### 6.2 `GET /v1/games`

```json
{
  "games": [
    {
      "gameId": "galaxy-crash",
      "name":   "Galaxy Crash",
      "rtpVariants": [97.0, 95.0, 92.0],
      "minBetMinor": { "EUR": 10, "USD": 10, "BTC": 100 },
      "maxBetMinor": { "EUR": 500000, "USD": 500000, "BTC": 100000000 }
    }
  ]
}
```

### 6.3 `POST /v1/sessions/{sessionId}/terminate`

Operator force-closes a player session (self-exclusion, RG limit hit, AML hold).

```json
{ "reason": "self_excluded", "message": "Session closed by operator." }
```

Response: `204 No Content`. The Game disconnects the WS, voids any in-flight bet via `/rollback`, and renders a message inside the iframe.

### 6.4 `GET /v1/rounds/{roundId}`

Operator support lookup for a single round. Returns bets, wins, seeds, settlement status.

### 6.5 `GET /v1/transactions?playerId=...&from=...&to=...&cursor=...`

Operator's view of all our transactions involving their player. Paginated. For dispute resolution.

## 7. Errors

All wallet endpoints use this error envelope on non-2xx:

```json
{
  "error": {
    "code":    "INSUFFICIENT_FUNDS",
    "message": "Balance 50 < bet 100",
    "balanceMinor": 50
  }
}
```

| HTTP | `code` | Meaning | Game behavior |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | Malformed body | Reject bet; log; alert |
| 401 | `INVALID_TOKEN` | Launch token bad/expired | Abort launch |
| 401 | `INVALID_SIGNATURE` | HMAC mismatch | Abort; alert ops |
| 403 | `PLAYER_BLOCKED` | RG / KYC / geo | Reject bet; show op message |
| 403 | `SESSION_EXPIRED` | Token TTL passed | Terminate session |
| 404 | `PLAYER_NOT_FOUND` | Unknown playerId | Reject bet |
| 409 | `INSUFFICIENT_FUNDS` | Balance < amount | Reject bet; show op-supplied msg |
| 409 | `BET_LIMIT_EXCEEDED` | Above max stake | Reject bet |
| 409 | `DUPLICATE_TXN` | Different body, same txnId | Game error → alert |
| 422 | `CURRENCY_MISMATCH` | Currency not enabled | Abort launch |
| 429 | `RATE_LIMITED` | Operator throttle | Back off; retry |
| 5xx | `UPSTREAM_ERROR` | Operator wallet down | Retry policy (§8) |

## 8. Retry & timeout policy

| Endpoint | Timeout | Retries | Backoff |
|---|---|---|---|
| `/authenticate` | 5 s | 1 | 250 ms |
| `/balance` | 3 s | 1 | 250 ms |
| `/bet` | 10 s | 3 | 500 ms, 1.5 s, 4 s |
| `/win` | 10 s | 5 | 500 ms, 1 s, 2 s, 5 s, 15 s |
| `/rollback` | 10 s | ∞ (until success) | 1 s → 5 s → 30 s capped, persistent queue |
| `/round-end` | 5 s | 1 | none (fire-and-forget) |

A `/win` that exhausts retries is escalated as a critical alert and queued for manual settlement — **the Game must NOT credit the player itself**.

A failed `/bet` aborts the bet placement client-side. A failed `/win` is the dangerous case; see §10.

---

## 9. Idempotency

- `txnId` is a v4 UUID (or KSUID) generated by the Game once, persisted before the call.
- Operators MUST dedupe by `(operatorId, txnId)`. Same body replayed → same response. Different body, same txnId → `409 DUPLICATE_TXN`.
- The Game persists `txnId` + state (`PENDING | OK | FAILED | ROLLED_BACK`) in the transaction log before issuing the call and updates on response.
- On Game restart, the recovery worker scans `PENDING` entries and retries them.

---

## 10. Round state machine

```
BETTING ──(/bet OK)──> ARMED ──(round starts)──> FLYING
ARMED ──(cashout)──> SETTLING ──(/win OK)──> SETTLED
ARMED ──(crash)──> LOST
ANY   ──(error)──> ROLLBACK_PENDING ──(/rollback OK)──> VOIDED
```

Persisted transitions: every state change is an append-only row in `bet_log`. On crash recovery, replay from the last durable state.

Invariants:
- A bet in `ARMED` cannot be lost (the operator already debited).
- A `SETTLED` bet has a matching `/win` operator receipt.
- A `VOIDED` bet has a matching `/rollback` operator receipt OR the operator returned `noop`.
- No bet ends in `PENDING` or `SETTLING` after the round closes. The reconciliation worker (§12) re-drives any stragglers.

---

## 11. Currencies & limits

- All amounts are integers in **minor units**.
- Decimal precision per currency is declared at operator onboarding (EUR=2, BTC=8, etc.).
- Per-operator, per-currency `minBet` and `maxBet` come from §6.2 but are also enforced server-side per request.
- Multi-currency operators can have different currencies per player; the Game NEVER converts — it uses whatever currency `/authenticate` returned.

---

## 12. Reconciliation

Daily at 00:15 UTC the Game's reconciler:
1. Fetches `GET /v1/operator-tx?from=T-24h&to=T` from the operator (operators MUST implement this for reconciliation).
2. Compares against the Game's `bet_log`.
3. Flags mismatches in the studio backoffice (§13 of plan) with a categorized reason (`missing_on_operator`, `missing_on_game`, `amount_mismatch`, `status_mismatch`).

Operators are notified via webhook on mismatch.

---

## 13. Testing & certification

A sandbox environment at `https://sandbox.galaxy-crash.io` is provided. Operators receive a stub credentials pair. The Game ships an operator stub server (`tools/operator-stub`) operators MAY run locally to develop against.

The Game ships an integration test harness (`tools/wallet-conformance`) operators run against their staging to verify:
- All 6 endpoints reachable, well-formed, signed correctly
- Idempotency on `/bet` and `/win`
- Rollback works for known and unknown `txnId`
- Insufficient-funds returns 409 (not 200 with zero balance)
- Currency in response matches request

A passing run is a prerequisite for production credentials.

---

## 14. Versioning

This spec is **v1**. Breaking changes will create `v2` at a parallel path (`/v2/`). Operators integrated against v1 remain supported for ≥ 12 months after v2 release.

Per-request `Accept: application/vnd.galaxy-crash.v1+json` is honored but optional; defaults to v1.

## Appendix A — Full happy-path example

```
1. Player clicks game thumbnail on casino.com.
2. Operator mints launch token "lt-abc".
3. Browser opens iframe at .../launch?operator=acme&token=lt-abc&currency=EUR
4. Game backend POSTs /authenticate {token: "lt-abc"} → playerId, balance 125075.
5. Game shows iframe, balance EUR 1250.75.
6. Player bets EUR 100. Game POSTs /bet {amountMinor: 10000, txnId: t1} → balance 115075.
7. Round runs. Player cashes out at 2.45×.
8. Game POSTs /win {amountMinor: 24500, multiplier: 2.45, txnId: t2} → balance 139575.
9. Game POSTs /round-end (fire-and-forget).
```

## Appendix B — Failure: /win times out

```
1-7. Same as A.
8. Game POSTs /win → connection times out at 10s.
9. Game retries (500ms, 1s, 2s, 5s, 15s). All time out.
10. Game escalates: writes bet_log row state=WIN_FAILED, alerts on-call.
11. Game UI shows player "Win pending — contact support."
12. On-call uses /v1/rounds/{roundId} from operator to confirm. If operator never received it, manual settlement via studio backoffice "force credit" tool (audited).
```
